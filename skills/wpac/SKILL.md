# WPAC 深度手册

人格段（persona）给的是骨架，这份手册给的是可直接抄用的零件：判定表、选项库、约束清单、模板、例句、评分表。

## 管线（先看这个）

每篇文字成品按 6 段走：**加载 → 问 → 角色卡 → 写 → 闸 → 交付**。完整表、每段出口闸、故障对照见 `references/管线.md`。

闸段自检完调 `wpac_structure_review` 把结构交给用户按模块确认；用户提交意见后按 moduleId 改对应段，再跑 preflight。

**文件类委托（PDF / PPT / Word / 表格）**：也走 wpac，但先分流——开头必须问一句「是否启用文件类 WPAC（实验性）」，用户选启用才按 F1–F5 走（问两轮 → 拆结构 → 弹窗确认 → 生成文件 → 文件自检），详见 `references/文件类-WPAC.md`。没问过、用户选不启用，就按普通方式做，不弹窗。弹窗确认时选中模块显示的是**这一页的预览截图**（模块 `preview` 字段先出 PNG）。

## 1. 四要素：什么叫"够了"

判定标准只有一条：**这条信息会不会改变产出**。会，就是缺；不会，就是够。

| 要素 | 不够（需要追问） | 够（可以开工） |
| --- | --- | --- |
| W | 帮我写个总结 | 我是 ToB SaaS 的实施顾问，给制造业客户写项目周报 |
| P | 写个方案 | 写 8 页方案，让客户 CTO 在周会上拍板是否采购 |
| A | 给领导看 | 集团副总裁，非技术背景，5 分钟内读完，只关心成本与风险 |
| C | 正式一点 | 公文语气，1500 字内，含 3 张表，数据只用附件，不提竞品名 |

补充判定：

- **P 不明时优先级最高**。目的决定受众，受众决定表达，表达决定约束；P 错了，后面全错。
- **A 的关键不是职位，是"判断标准"**：他凭什么点头、凭什么否掉。
- **W 不是简历**：只取与主题相关的身份、立场、可调用素材。用户没说的身份不要编。
- **C 要区分硬约束与偏好**：硬约束（字数、格式、截止、禁用词）先记；偏好（"活泼一点"）转成可执行描述（短句、口语、每段一个例子）。

## 2. 追问：文字成品固定四轮 W → P → A → C，一个都不许跳

**顺序是硬的**：W（你是谁）→ P（要什么）→ A（给谁）→ C（约束）。一次只问一个槽，
问完就停、等回答；不要把四个槽合成一次问，也不要自问自答或边问边写。

每个槽的标准问法（都带 3-4 个选项）：

- **W**：「这篇东西是你自己写、署你的名吗？」→ 学生作业 / 工作汇报 / 个人号发文 / 代笔。
- **P**：「写出来主要拿去干什么？」→ 交作业 / 交差 / 对外发布 / 自己留着。
- **A**：「给谁看？」→ 老师 / 上级 / 客户 / 普通读者。
- **C**：「有什么硬要求？」→ 字数、格式、截稿、不能提的东西（可多选）。

规则：

1. 四轮每一轮都要问；原话里已说过的槽改成确认式再问一遍，不跳过。
2. 每题 3-4 个选项，选项之间要真正互斥，每个选项后跟一句差异说明。
3. 留「其他（我来说）」的口子，方便自填。
4. 用**产出语言**问，不用术语：「这份东西最后给谁看」而不是「目标受众是谁」。
5. 四轮走完才动笔；少于四轮就写正文算违规。用户说「别问了 / 直接写」→ 全部用默认值，立刻写。

现成选项库（可直接搬）：

**P｜这份东西最终用来做什么？**
- 直接发布（公众号 / 官网 / 社媒）
- 给人过审（领导 / 客户 / 法务）
- 自己决策参考（不上台面）
- 交下游继续加工（设计 / 开发 / 翻译）

**P｜怎样算做成？**
- 对方当场点头 / 签字
- 读者读完能复述核心观点
- 能直接发出去，不用再改
- 先有个能讨论的版本

**A｜谁看 / 谁验收？**
- 上级或甲方（要结论、要风险）
- 同行专家（要严谨、要边界）
- 普通读者（要例子、要说得具体）
- 机器或流程（要结构、要字段）

**A｜他们现在知道多少？**
- 完全不了解，需要铺垫
- 知道个大概，需要说服
- 很懂，只想看新增信息
- 有预设立场，需要拆解反对意见

**C｜硬约束有哪些？**（多选）
- 字数 / 页数
- 截止时间
- 必须包含的材料或数据
- 不能提的人、事、竞品、承诺

**C｜表达上最不能接受什么？**
- 太官方、像通稿
- 太口语、不够专业
- 术语太多看不懂
- 空话多、没有例子

**W｜署名的是谁？**
- 本人（我补充身份）
- 团队 / 公司名义
- 代笔，按对方口吻
- 匿名 / 不署名

### C 轮细分：C1 形式 → C2 内容 → C3 提交（→ C4…）

C 不再一次问完，拆成 C1 → C2 → C3（→ C4…），一轮一问，全部 `multi_select: true`（含 C4/C5/C6）：

- C1 形式（8–10 项）：字数 800–1000 / 1000–1200 / 1500+；纯段落 / 允许小标题；标题自拟 / 题目从给定选项里选；落款 / 不落款；其他。
- C2 内容（8–10 项）：细节只用概括 / 细节我来给 / 要真实经历；不堆口号；不出现某人名机构；必含某材料；第一人称；口语度。
- C3 提交与检测（8–10 项）：截止日期 / 渠道 / 查重 ≤20% / AI 率 ≤20% 或 ≤10% / 附参考资料 / **继续补充其他要求（进入 C4）** / 其他。

C3 起，每轮必须带「继续补充其他要求（进入下一轮）」：C3→C4→C5→C6 依次出现（C4 写「进入 C5」，C5 写「进入 C6」）；C6 是最后一轮（上限 6 轮），不再给「继续补充」，只留「没有了（结束）」和「其他（我补充）」。**发出去之前数一遍：C3 少「进入 C4」= 错；C4/C5 少「继续补充」或「没有了」= 错；少一个就重发。** C4 起的选项：必含材料 / 指定题目 / 不写真实姓名 / 附参考资料 / 没有了 / 继续补充。

细节见 `references/C轮选项库.md`；选项只写具体可选项，日期 / 格式 / AI 率没定的别造选项——不要写「其他」「其他（你填）」这类占位项（界面自带自定义输入框）。

### 执行中卡住了怎么办

四种卡点，只有前三种值得停：

| 卡点 | 判据 | 怎么做 |
| --- | --- | --- |
| 文件 / 数据不在 | 路径不对、没权限、内容为空 | 先自查一次（glob / 换路径），确实没有就停，问「贴数据 / 换来源 / 我用占位」 |
| 口径冲突 | 用户前后要求互斥（800 字 vs 300 字） | 停，把冲突摆出来，让用户选一个；不要自己挑一个继续写 |
| 工具不可用 | 需要的工具加载不出来 / 执行报错 | 先试一次替代路径（load_tools、换工具），还不行就停，问「降级做着 / 等工具 / 换目标」 |
| 范围超预期 | 做着发现要 10 小时而不是 10 分钟 | 不停，先交付一个能用的最小版本，末尾写清"还差什么" |

卡住时的消息模板（≤5 行，一次只问一件）：

```
【卡在】<一句话说清卡在哪>
已完成：<1-2 项，说明成果还在>
需要你定：
1. <选项 A> — <差异>
2. <选项 B> — <差异>
（其余部分我先按 <默认> 继续）
```

三条纪律：

1. **只问卡住的那一项**，不要借机把整个需求再审一遍。
2. **成果保留**：已写的段落、已跑通的部分不动，恢复后从那一步接上。
3. **不猜**：数据、口径、人名、金额，宁可用 `[待补：xx]` 也绝不填一个像真的假值。

## 3. 约束清单（挑相关的写进提示词，不要全抄）

### 情景约束
时间与节奏｜篇幅与页数｜发布渠道（公众号 / 邮件 / 会议 / 内网 / 印刷）｜预算与人力｜素材来源与可用范围｜数据时效｜合规与审批｜保密级别｜竞品提及限制｜地域与文化语境｜团队协作方式｜交付节点｜甲方既有模板｜历史版本沿用｜法务口径｜品牌规范｜技术环境（平台 / 版本 / 兼容）｜上线窗口｜培训与交接

### 表达约束
语气（正式 / 专业 / 亲和 / 犀利）｜人称（我 / 我们 / 笔者 / 本司）｜术语密度｜句长节奏｜段落长度｜标题风格｜是否用列表｜图表比例｜举例密度｜幽默尺度｜情绪强度｜立场鲜明度｜中英混排规则｜标点规范｜称谓与敬语｜口语化程度｜是否允许第一人称判断

### 产出约束
文件类型（md / docx / xlsx / pptx / 代码）｜结构骨架（章节与顺序）｜字数区间｜必含项（结论 / 数据 / 风险 / 附录）｜禁止项｜命名与目录规范｜引用格式｜验收清单｜是否需要可直接复制的版本｜是否需要演示稿｜是否需要多语言｜是否需要图表｜版本号与日期

## 4. 提示词模板（把尖括号换成实际内容）

### 5.1 通用写作
```
你是<角色>，为<受众>写一份<交付物>，目的是<目的>。
背景：<3-5 条事实/素材>
结构：<开头钩子> → <2-4 个主体段落，每段一个观点 + 一个例子> → <结尾行动或判断>
约束：<字数>；<语气>；<必须出现的内容>；<禁止出现的内容>
验收：读者能复述<核心观点>；不含空话；每个观点有例子或数据。
```

### 5.2 公文 / 汇报
```
写一份<文种>，报送<对象>，事项是<一句话>。
要求：结论先行；三段式（结论 / 依据 / 请示事项）；600-900 字；数据只用<来源>；
不出现形容词堆砌；不用"高度重视""大力推进"这类套话；末尾给<时限>与<责任人>。
```

### 5.3 学术 / 论文段落
```
在<领域>中，就<问题>写一段<文献综述/方法/讨论>，面向<同行读者>。
必须：引用<作者年份>的观点并给出边界；区分事实与推论；术语与<既定译名>一致；
不要第一人称泛滥；不要绝对化结论；段落间有逻辑连接词但不使用"首先其次"。
```

### 5.4 营销文案
```
为<产品>写<渠道>文案，受众是<画像>，他们现在的痛点是<痛点>。
结构：痛点场景 → 我们的做法 → 证据（数据/案例/对比） → 行动指令。
约束：<字数>；口语；不夸张承诺；不出现"颠覆""革命性"；品牌名<名称>。
```

### 5.5 代码任务
```
在<仓库/语言/框架>中实现<功能>。
约束：不引入新依赖（或：可用<依赖>）；保持<现有风格>；错误处理覆盖<场景>；
给出改动文件清单与关键 diff；附<测试方式>；不改变<现有行为>。
验收：<命令> 通过；<边界用例> 有覆盖。
```

### 5.6 方案 / 决策
```
就<决策点>给出一页纸建议，读者是<决策人>。
结构：结论（选哪个）→ 三个理由（每个带数据）→ 主要风险与对冲 → 备选方案与放弃原因。
约束：不超过 800 字；不写正确但无用的话；不确定的地方标注置信度。
```

### 5.7 教学 / 科普
```
把<概念>讲给<基础水平>的人听。
要求：先给一个他们熟悉的类比；再给准确定义；再给一个反例；最后给一个可操作练习。
约束：<字数>；不堆术语；每段不超过 4 行；允许一个比喻贯穿全文。
```

### 5.8 个人 IP 口播 / 短文
```
以<身份>的口吻，讲<一件事>，面向<粉丝画像>。
要求：第一句就是钩子（反常识/具体场景/数字）；全文口语；每 2-3 句一个停顿；
有一个个人经历；结尾一句态度，不喊口号。约束：<时长/字数>。
```

## 5. 一个走完的样例

**用户原话**：「帮我写个季度总结，给老板看。」

**判型**：公文 / 汇报 → 文字成品，走四轮。

**四轮追问**（一轮一题，问完等回答）：

- 第 1 轮 W「你以谁的身份写这份总结？」：实施顾问 / 项目负责人 / 部门助理 / 其他。
- 第 2 轮 P「写出来拿去干什么？」：交给直属上级过目 / 部门例会汇报 / 存档。
- 第 3 轮 A「给谁看、谁验收？」：直属上级（懂业务）/ 事业部负责人（看结果与风险）/ 老板本人（只看结论）。
- 第 4 轮 C「硬要求有哪些？」：800-1000 字 / 必须带数据表 / 不能提竞品 / 本周五交（可多选）。

**用户答完**：实施顾问；交给直属上级；他懂业务、关心回款；800-1000 字、带数据表。

**优化后提示词**（存 `wpac/20261029-q3-summary.md`）：

```
角色：我是 SaaS 实施顾问，负责 3 个制造业客户。
任务：写 Q3 工作总结，交给直属上级（懂业务、关心延期与回款）。
素材：q3.csv（进度、工时、回款）；不编造任何数字。
结构：结论 → 三个项目的进展与卡点 → 数据表 → Q4 要资源。
约束：800-1000 字；公文语气但句子口语；不写"高度重视"；不出现竞品名。
验收：上级 3 分钟读完，能判断要不要给资源。
```

**交付**：只有正文；若存了文件，末尾最多一行说明。

## 6. 产出前唯一清单（12 条，合并了原评分表与交付清单）

逐条过，任一条不过就地改，不要把清单甩给用户。

1. 文字成品交付前走完四轮（四要素齐全也要走，原话已给的槽用确认式复问）。
2. 正文没有 WPAC / 简报 / 「以下是」字样，没有多余小标题、列表、序号。
3. 回复里除正文外没有附加（说明、字数、括号备注、结尾客套）；交付文件时最多一行说明。
4. 拿去就能用，不是思路或初稿。
5. 目标达成，成功标准可检验。
6. 受众的认知起点与雷区都照顾到。
7. 篇幅、渠道、时间、素材合规。
8. 语气、人称、术语、格式统一。
9. 有细节、有判断，不空泛。
10. 事实、数字、引用可追溯，无编造，待补的地方标明。
11. 与确认过的 WPAC 一致，没有偷偷改需求。
12. 文件已用 present 交付（若为文件），字数达标。

## 6.5 结构模块怎么划（弹窗里给用户看的那 4–8 块）

交付前 `wpac_structure_review` 交的 modules 不是切段落，是**任务结构**：每块说清它在整篇里干什么活。先按任务类型挑骨架，再按实际内容改成这块的事：

- 观后感 / 心得：到场（预期落空）→ 看到的物 / 人 / 事 → 难在哪（细节）→ 见到本人（如有）→ 口号对不上 → 我的自省 → 收束（不升华）
- 记叙 / 小说：场景 → 人物要什么 → 卡点 / 冲突 → 转折 → 代价 → 收束（留白）
- 公文 / 汇报：背景 → 做法（分条）→ 成效 / 数据 → 问题 → 下一步 → 请示 / 收尾
- 口播 / 短视频：钩子 → 反常识 / 冲突 → 例子 / 论证 → 落点（一句落到人的话）
- 提案 / 方案：问题 → 目标 → 方案（2–3 条）→ 代价 / 风险 → 谁做什么 → 时间点 → 拍板请求
- 学生作文：一个具体场景开头 → 事情 → 转折处的一个细节 → 我怎么想 → 收在一件小事上

三条硬规矩：① 一块只说一件事，别把两段并成一块；② title 写「这块干什么」（如「难在哪」），不是写内容（如「抓斗的历史」）；③ summary 一句话落到具体事实，空话（「展现了精神」）不算。④ 每块还要给 `text`：这一块的原文照贴，不要摘要——弹窗右侧点开模块看到的就是它，摘要糊弄不过去。

**文件类交付怎么拆**：PPT 一块=一页、Word/PDF 一块=一节/一页、表格一块=一张表/一个区域；`format` 用 `slides` / `document` / `pdf` / `table`。完整问题库、骨架表、文件自检清单见 `references/文件类-WPAC.md`（含常见坑：先建文件再问、format 写错、text 写摘要、页数不达标、PDF 字没嵌、Excel 公式写死）。

## 7. 工具适配矩阵

| 场景信号 | 用什么 | 纪律 |
| --- | --- | --- |
| 读写本地文件、找代码 | read / write / edit / glob / grep | 先读后写；大文件分段读 |
| 跑命令、跑测试、装依赖 | bash | 一次一条明确命令；失败看退出码 |
| 需要事实、数据、引用、竞品 | web（search + fetch） | 关键结论至少两个来源；查不到写"未核实" |
| 缺 W/P/A/C | ask_user_question | 一轮 1 题，给选项，问完等回答 |
| ≥3 步的任务 | todo_write | 开工前建，做完立即勾 |
| 需要长文档 / 模板 / 例句 | skill（wpac / 其他） | 手册按需加载，不要一开始全塞 |
| 并行调研、多方案对比 | subagent / workflow | 主结论自己收敛；子代理结果要交叉验证 |
| 交付文件 | present + 对应格式工具 | 文件路径用绝对路径，正文内联展示 |
| 图像 | sd_*（有则用） | 提示词英文；图必须与正文对得上 |
| 表格 / 文档 / 幻灯片 | univer_* / office | 先确认结构再写内容 |
| 跨会话记忆 | memory | 只存稳定事实与偏好 |
| 长周期目标 | goal | 目标可验证，别写口号 |

工具总原则：**能一次拿全的不拆成五次；与产出无关的工具输出不进正文；工具失败时改路而不是硬撞。**

## 8. 身份与场景写法

**先问再写**：任何文字成品，交付前必须有提问环节（新写 1–4 题、改稿至少 1 题）。没问过就写，是最严重的违约。

**按身份定腔调**：

| 身份 | 不要 | 要 |
| --- | --- | --- |
| 大一新生 / 学生 | 小标题、序号、加粗小结、"综上所述" | 第一人称、具体场景（教室/宿舍/食堂）、结尾落在个人感受 |
| 公文 / 汇报 | 感叹号、随意的口头语 | 结论先行、分节、数据支撑 |
| 自媒体 | 学术腔、长句 | 钩子开头、短句、每段一个意思 |
| 学术 | 绝对化、随意的口头语 | 引用、限定、术语一致 |

**具体细节优先**：开头写一个具体时刻，不写"随着……的发展"；每段至少一个能看见的东西（课表、食堂的菜、宿舍的灯）。

### W 角色卡（S3 用，不给用户看）

W 定了，先填一张卡（模板见 `references/W角色卡.md`）：**我是谁 / 我关心什么 / 我不懂什么 / 我会怎么讲 / 我不能写什么**。

- 大一新生：不知道政策细节、没进过码头、不会说「验收人」「底层逻辑」「范式」；看到抓斗只会想「这不就是个夹子」。
- 写到超出他认知的：改成「听讲解说」「展板上写」「我后来查了一下」，或者不写。
- 口吻：用他这个年纪会用的词；不会用的词，宁可不写。
- 判断也要入戏：他的判断可以是错的、片面的，不要给他安一个专家的结论。
- **旁观摘要不写**：「见到人了，话没听清几句」「展厅不大，一圈二十分钟」——谁见谁、听没听清，跟「我」没关系；删掉，或换成「我」的处境。
- 段落比例：至少一半段落从「我」出发；包起帆生平最多 2 段，每段回到「我」。


## 9. 反模式

1. 一上来就问 8 个问题——用户会烦；先给默认值 + 只问关键项。
2. 简报写 30 行——简报是给用户确认的，不是给你自己看的。
3. 把"优化后的提示词"当成最终产出——用户要的是结果，提示词是附属物。
4. 堆形容词冒充"极致"——极致是具体、可验证、有取舍。
5. 用工具凑工作量——每个调用都要能解释"为什么需要它"。
6. 自检写成汇报——自检是自己做的，不是让用户做的。
7. 编一个用户身份继续写——宁可留占位。
8. 通篇排比句、四字词——最像 AI 的写法。
9. 交付说明啰嗦——正文外不加任何说明，文件最多一行。
10. 用户说"直接来"还贴简报——尊重指令。

## 10. 成稿前自检：七个已知故障

1. **技能加载了吗？** 没加载就回去加载再写。
2. **有没有编用户没给的东西？** 个人经历、现场细节（签到、照片、小册子、明天的事）——有就删，或先问用户。
3. **数字 / 奖项超过 3–4 个了吗？** 超了就砍到能支撑判断的量，别罗列。
4. **总说 + 分说的地方，逗号该改冒号吗？**
5. **结尾是点题 / 动作，还是总结升华？** 总结就改。
6. **硬要求逐条对了吗？** 字数、禁项、选题、细节来源、截止——漏一条就重写那一条。
7. **W 对得上吗？** 换成另一个人，这些话还说得出来吗；至少一半段落从「我」出发。

### 输出前 gate（必做）

1. 草稿写 `/tmp/wpac-draft.txt`。
2. `node ~/.dsh/skills/wpac/scripts/preflight.mjs --min <下限> --max <上限> /tmp/wpac-draft.txt`（用户说概括 / 没给细节时加 `--no-details`，展品、引语、个人动作、自己的事都会算 FAIL）
3. 红了按提示改，改完再跑；全绿再发。
4. 事实清单：每个具体展品 / 年份 / 数字 / 个人动作 / 真人引语 / 自己的事，能指到用户原话或核对链接吗？指不到就删，或改成概括。
